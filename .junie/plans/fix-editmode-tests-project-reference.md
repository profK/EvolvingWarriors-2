# Technical Diagnosis

### Root Cause
The `EditModeTests.csproj` is missing a `<ProjectReference>` to `Assembly-CSharp.csproj`. All three missing types exist in the Assembly-CSharp project:

- `IBoneTransformProvider` — defined in `Assets/Components/Warrior/WarriorBoneController.cs`
- `ProceduralFootController` — defined in `Assets/Components/Animation/ProceduralFootController.cs`
- `WarriorPoseSolver` — defined in `Assets/Components/Animation/WarriorPoseSolver.cs`

The `EditModeTests.asmdef` file correctly lists `Assembly-CSharp` as a reference, and these source files are compiled into the `Assembly-CSharp` project (verified in `Assembly-CSharp.csproj`). However, Unity's csproj generator did not produce a corresponding MSBuild `<ProjectReference>` in `EditModeTests.csproj`, so the Rider/MSBuild build cannot resolve the types.

Additionally, the solution file (`EvolvingWarriors 2.sln`) lacks a `SolutionDependencies` section, meaning there's no build-order guarantee that Assembly-CSharp builds before EditModeTests.

### Proposed Changes
1. **EditModeTests.csproj**: Add a `<ProjectReference>` to `Assembly-CSharp.csproj` in a new `<ItemGroup>` before the `<Import>` statement.
2. **EvolvingWarriors 2.sln**: Add a `GlobalSection(SolutionDependencies)` section establishing that EditModeTests depends on Assembly-CSharp.

Both files are auto-generated by Unity, but the fix is safe: Unity's regeneration will preserve the asmdef reference, and the ProjectReference is the correct MSBuild representation of that asmdef dependency. If Unity regenerates without the reference, the user may need to re-apply after regeneration or use a post-generation script.
